03 / C

C

Direct, but manual.

Plain data and visible control flow. Dynamic storage adds chores.

What worked well

  • Structs and functions are easy to trace.
  • Sokol and shared audio use C interfaces directly.
  • Layout and allocation behavior are visible.

What cost us

  • Typed lists repeat growth and removal code.
  • Error handling and event validity depend on conventions.

Collection shape · from game.h

typedef struct EnemyList {
    Enemy *data;
    size_t count, capacity;
} EnemyList;

Our helpers must grow, append, compact and free this storage.

grow fails→failure flag→host checks

This repetition is a design choice. C could use collection macros or a library, and a manually tagged event union.

04 / Odin

Odin

Less machinery.

The gameplay stays direct while common data handling gets shorter.

What worked well

  • Built-in dynamic arrays and generic helpers replace repeated C code.
  • Vector arithmetic keeps movement readable.
  • Tagged events and enum-indexed arrays express intent.

What cost us

  • Allocator context is less visible at call sites.
  • Temporary lifetimes and optional allocation errors need care.

Collection shape · from types.odin

enemies: [dynamic]Enemy,
bullets: [dynamic]Bullet,
events:  [dynamic]Event,

// Each array carries its allocator.

A generic push handles append errors; one generic compaction helper serves all entity lists.

append error→record error→host checks

Our C audio binding is handwritten. Native callbacks restore Odin’s context, and temporary formatting storage is reset after use.

05 / Zig

Zig

Make failure visible.

Allocation and errors are part of the interface, all the way up.

What worked well

  • Explicit allocators, try, defer and errdefer clarify failure and cleanup.
  • Built-in allocation-failure testing helps verify ownership.
  • The build translates our actual C audio header.

What cost us

  • Casts and error/allocator plumbing add visual noise.
  • Build and library calls needed version-specific adaptation.

Appending an event · from game.zig

try g.events.append(g.allocator, .{
    .sound = .{ .id = id, .gain = gain },
});

// Allocation and failure are visible here.

Errors propagate through gameplay helpers. The application catches the error and shuts down cleanly.

append error→try propagates→host catches

Explicit error handling does not enforce unique ownership or make pointers survive collection growth.

06 / The architectural limit

What about 30 enemy types?

Your earlier criticism still applies to every version.

The language helps with expression.

COdinZig

Collections, math, events and errors become more or less convenient.

Same state machines + enemy-kind switches

More content needs a design decision.

→× 30

We would need to decide how enemy data, behavior and graphics are described and combined.

All three still need lifetime discipline. Don’t copy a live owning Game or retain element pointers across growth. Replay reuses storage; allocation failure ends the run.

This experiment exercises growable lists, not complex object graphs or concurrent ownership.

08 / The conclusion

For this game, I’d pick Odin.

The best balance of readable gameplay and convenient data handling in these ports.

C

Most direct foundation

Easy to follow, with the most manual collection machinery.

Odin

Best balance here

Less plumbing, while keeping the game logic straightforward.

Zig

Clearest failure paths

Allocation and cleanup are easier to audit, with more syntax to read.

Dynamic data exposed the language tradeoffs.
More ambitious content would expose the architecture.

A judgment about this small experiment, not a universal ranking. The original fixed-array C version remains tagged c-original-reference.
